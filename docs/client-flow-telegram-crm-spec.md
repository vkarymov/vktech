# VKTech — Client Flow / Telegram Bot / Project Control

**Статус:** Approved specification
**Зафиксировано:** 2026-10-04
**Назначение:** это исходное ТЗ для дальнейшей реализации. Любые изменения scope во время разработки должны явно сверяться с этим документом, а не молча менять архитектуру.

## 1. Общая архитектура

Сайт VKTech и Telegram-бот являются двумя клиентскими интерфейсами одного backend/API.

```text
Web / vktech.uz ─┐
                 ├─> VKTech API ─> PostgreSQL
Telegram Bot ────┘
                         │
                         └─> Admin Telegram interface
```

Ни сайт, ни Telegram-бот не должны напрямую работать с PostgreSQL.

Backend содержит бизнес-логику. PostgreSQL является единым source of truth. Web и Telegram — адаптеры и интерфейсы одной системы.

## 2. AI/LLM

В клиентском чате AI/LLM **не используется**.

Диалог детерминированный:

- стандартные подсказки;
- кнопки;
- наводящие вопросы;
- ветвление в зависимости от услуги;
- state machine;
- возможность вернуться назад и исправить ответ.

Цель — быстро собрать достаточную информацию о потенциальном заказе, а не имитировать AI-собеседника.

## 3. Общий Client Flow

Web и Telegram используют одну бизнес-логику Client Flow.

Пример последовательности:

1. Что требуется: сайт, Telegram-бот, автоматизация, интеграция или другое.
2. Уточняющие вопросы в зависимости от направления.
3. Описание задачи.
4. Желаемые сроки.
5. Ориентир бюджета, если уместно.
6. Имя.
7. Способ связи.
8. Материалы и файлы — опционально.
9. Предпросмотр собранной карточки.
10. Подтверждение.

Не превращать Client Flow в длинную анкету. Собирать только данные, реально необходимые для оценки проекта и дальнейшего контакта.

## 4. Файлы и материалы

Telegram-клиент может отправлять PDF, изображения, документы, таблицы, архивы, ТЗ, референсы и другие материалы.

Для Telegram хранить Telegram `file_id`, metadata и связь с conversation/lead. Не хранить бинарные файлы непосредственно в PostgreSQL без отдельной необходимости.

Материалы должны быть доступны из admin-карточки лида.

## 5. Финал Client Flow

После сбора данных клиент видит итоговую карточку и две основные кнопки:

```text
[ ХОЧУ ОБСУДИТЬ ЗАКАЗ ]
[ ЕСТЬ ВОПРОС ]
```

Обе кнопки передают карточку Вадиму и вызывают admin alert. Различается intent:

- `ORDER`;
- `CONSULTATION`.

Пользователь не должен теряться только потому, что ещё не готов формально оформить заказ.

## 6. Lead

После завершения Client Flow создаётся или финализируется Lead.

Логически Lead должен содержать как минимум:

- `id`;
- `source`: `WEB` / `TELEGRAM`;
- `intent`: `ORDER` / `CONSULTATION`;
- `name`;
- `contact`;
- `service_type`;
- `description`;
- `budget`;
- `desired_deadline`;
- `created_at`;
- `status`;
- `conversations`;
- `attachments`.

Это логическая схема. Не менять существующие модели вслепую: сначала сопоставить её с текущей backend-моделью.

## 7. Admin alert

После любого финального действия клиента Вадиму немедленно приходит Telegram alert с карточкой.

Карточка должна показывать:

- ID;
- источник;
- intent;
- имя;
- контакт;
- услугу;
- описание задачи;
- бюджет;
- срок;
- количество или список материалов.

Основные действия:

```text
[ КАРТОЧКА ]
[ МАТЕРИАЛЫ ]
[ ВЗЯТЬ В РАБОТУ ]
[ ОТКАЗАТЬ ]
```

## 8. Взять в работу

`[ ВЗЯТЬ В РАБОТУ ]` означает переход `Lead -> Project`. Проект становится `ACTIVE`.

После принятия клиент автоматически получает уведомление примерно следующего смысла:

> Ваш заказ принят в работу.
>
> Статус проекта, текущий этап и сроки можно посмотреть в меню бота или командой `/status`.
>
> Для личного общения, пожеланий, дополнительных материалов или правок можете написать мне напрямую: `@WORK_ACCOUNT`.

Конкретный username рабочего Telegram-аккаунта пока не хардкодить до отдельного подтверждения.

## 9. Рабочая личка

После принятия проекта клиенту предоставляется отдельный рабочий Telegram-аккаунт Вадима. Бот не должен пытаться заменить полноценный личный Telegram-диалог.

В интерфейсе клиента должна быть кнопка:

```text
[ НАПИСАТЬ ВАДИМУ ]
```

Она открывает рабочий Telegram account.

Разделение:

- бот — заявки, материалы, статусы и системные уведомления;
- рабочая личка — человеческое общение;
- backend/PostgreSQL — source of truth.

Основной личный Telegram-аккаунт не использовать для этого workflow.

## 10. Статус проекта для клиента

После принятия заказа клиент получает пункт меню `МОЙ ЗАКАЗ`. Также поддерживается shortcut `/status`.

Оба показывают один и тот же актуальный Project из backend. Минимально показывать:

- project ID;
- статус;
- название или тип проекта;
- дату принятия;
- deadline;
- текущий этап;
- дату и текст последнего обновления;
- кнопку обновления;
- кнопку связи с Вадимом.

Telegram не должен хранить отдельную независимую копию состояния проекта.

## 11. Отказ от лида

В admin interface обязательно действие `[ ОТКАЗАТЬ ]`.

После нажатия бот просит Вадима вручную написать причину отказа свободным текстом. Свободный текст сохраняется без изменений. После этого выбирается нормализованная категория:

- `БЮДЖЕТ`;
- `КЛИЕНТ`;
- `НЕ МОЙ ПРОЕКТ`;
- `ПЕРЕДУМАЛ`;
- `СПАМ / ТЕСТ`;
- `ДРУГОЕ`.

Логически сохранять:

- `rejection_reason`;
- `rejection_category`;
- `rejected_at`;
- `rejected_by`.

Свободный текст нужен для контекста, категория — для статистики.

## 12. REJECTED != CANCELLED

Это разные события:

- `REJECTED`: Lead отклонён до начала проекта;
- `CANCELLED`: Project уже был принят в работу, но затем прекращён.

Для `CANCELLED` также хранить свободную причину, категорию, кто инициировал отмену и дату отмены.

Возможные категории отмены:

- `CLIENT_CANCELLED`;
- `NON_PAYMENT`;
- `SCOPE_PROBLEM`;
- `ADMIN_CANCELLED`;
- `OTHER`.

## 13. Закрытый Admin Telegram interface

Telegram-бот имеет отдельный административный интерфейс для Вадима. Доступ определяется разрешённым Telegram user ID. Не использовать «секретную команду» как механизм авторизации.

Обычные пользователи административные функции видеть не должны.

В перспективе admin interface содержит:

- лиды;
- проекты;
- дедлайны;
- финансы;
- статистику.

## 14. Управление проектами

Из admin Telegram interface должно быть возможно:

- смотреть новые лиды;
- открывать карточку лида;
- смотреть материалы;
- принимать лид в работу;
- отказывать;
- смотреть активные проекты;
- устанавливать и изменять deadline;
- обновлять клиентский статус и этап;
- закрывать проект;
- отменять проект;
- в дальнейшем фиксировать оплаты.

Базовый lifecycle:

```text
LEAD
├── REJECTED
└── ACCEPTED
    └── ACTIVE
        ├── CANCELLED
        └── COMPLETED
```

Конкретная реализация enum/status должна учитывать существующую архитектуру и миграции.

## 15. Финансы

Не хранить финансовую историю непосредственно как набор полей Lead.

Предусмотреть отдельную сущность уровня `ProjectPayment`. Она должна позволять в дальнейшем хранить:

- project;
- amount;
- currency;
- payment date;
- payment type;
- comment.

Это необходимо для нескольких платежей, предоплаты и нормальной статистики.

## 16. Admin statistics

Статистика доступна только Вадиму.

В перспективе admin bot должен показывать:

**Проекты:** активных, ближайшие дедлайны, просроченные, завершённые и отменённые.

**Лиды:** всего, принято в работу, отказано, conversion `Lead -> Project`, причины отказов, источники `WEB` / `TELEGRAM`.

**Финансы:** заработано за текущий месяц, выбранный период и всё время; в дальнейшем — средний чек и другие производные показатели.

Пример будущего admin dashboard:

```text
VKTECH // CONTROL

Активных проектов: 4
Дедлайн <= 7 дней: 2
Просрочено: 1
Закрыто: 17

Заработано за месяц: ...

[ ЛИДЫ ]
[ ПРОЕКТЫ ]
[ ДЕДЛАЙНЫ ]
[ ФИНАНСЫ ]
```

## 17. Web использует ту же модель

Web chat не является отдельной CRM. Web и Telegram должны создавать лиды через один backend и одну бизнес-логику.

```text
WEB ───────┐
           ├── Client Flow -> Lead -> Project
TELEGRAM ──┘
```

Независимо от источника Вадим получает одинаковую admin-карточку.

В будущем web может показывать клиенту status Project через безопасный token/link без обязательного полноценного аккаунта.

## 18. Существующий backend

Backend уже существует.

До реализации необходимо изучить фактический код и существующие модели/миграции. Из предыдущего этапа ожидается наличие основы:

- sessions;
- conversations;
- messages;
- leads;
- handoff tokens;
- PostgreSQL;
- Alembic;
- API;
- Docker integration;
- nginx `/api/` routing;
- tests.

Не переписывать backend с нуля. Новое ТЗ должно расширять существующую архитектуру.

Если фактический код отличается от ожиданий документа — сначала зафиксировать отличие, а не молча перестраивать систему.

## 19. Scope VKTech v1

Для закрытия VKTech v1:

**Client:**

- Telegram bot;
- web chat;
- общий deterministic Client Flow;
- подсказки и наводящие вопросы;
- сбор контактов;
- Telegram attachments;
- итоговая карточка;
- «Хочу обсудить заказ»;
- «Есть вопрос».

**Backend:**

- единый Lead;
- source/intent;
- admin alert;
- принятие в работу;
- отказ со свободной причиной и категорией;
- Project;
- основные статусы;
- deadline;
- client-visible project status.

**Client Telegram:**

- `/status`;
- «Мой заказ»;
- уведомление о принятии;
- ссылка или кнопка на рабочую личку.

**Admin Telegram:**

- новые лиды;
- карточка;
- материалы;
- «Взять в работу»;
- «Отказать»;
- причина и категория отказа;
- просмотр активных проектов;
- базовое изменение статуса.

## 20. Не блокирует v1 / последующая итерация

Не раздувать текущий scope следующими возможностями. После v1 отдельно:

- расширенная финансовая статистика;
- графики;
- подробная аналитика конверсии;
- сложные milestones;
- расширенный web project-status;
- дополнительные client channels;
- расширенная автоматизация финансов.

Архитектура должна позволять это добавить, но реализовывать сейчас только если это необходимо для корректного v1 foundation.

## 21. Главный архитектурный принцип

> **Telegram и Web — интерфейсы.**
> **Backend — бизнес-логика.**
> **PostgreSQL — единый источник истины.**
> **Admin Telegram interface — пульт управления.**
> **Рабочая Telegram-личка — человеческое общение.**

Не дублировать бизнес-логику между Web и Telegram.

## 22. Planned v2 — VKTech Control

После завершения VKTech v1 планируется отдельная итерация v2.

Основное направление v2:

- заменить или дополнить текущий административный Telegram-интерфейс приватным Telegram Mini App `VKTech Control`;
- перенести в Mini App удобное управление лидами, проектами, дедлайнами, финансами и статистикой;
- Telegram Bot при этом оставить каналом Client Flow, системных уведомлений и admin alerts;
- предусмотреть Project Log / техническую историю проекта;
- Project Log должен позволять хранить компактные записи о выполненных этапах, milestones/releases/status changes и при необходимости связывать их с Git commit SHA;
- полную историю Git/repository в PostgreSQL не копировать;
- предусмотреть `INTERNAL` / `CLIENT` visibility для записей Project Log;
- CLIENT updates в дальнейшем могут использоваться для отображения истории прогресса клиенту;
- автоматическую Git/GitHub integration и webhooks рассматривать отдельно после появления базового Project Log.

Всё перечисленное в этом разделе относится к planned v2 и не должно расширять scope или задерживать завершение v1. Текущее v1 ТЗ в разделах 1–21 не переделывать под Mini App. Admin Telegram interface остаётся допустимой реализацией v1.
